- `validateRoadmap` adds `FEATURE_IN_TWO_CAPABILITIES`: the same catalog feature mapped in two capabilities of one roadmap. The schema only rejects a duplicate inside one capability, but materialisation upserts `app_features` unique on (target, catalog feature) with ONE capability (ROADMAP-PROTOCOL.md section 5 step 4), so such a roadmap cannot materialise.
- `validateRoadmap` cannot check "catalogs are per repository" (G-54): the catalog map carries no repository. The control plane already loads only the roadmap repository's catalog, which satisfies the rule.

Any planning-template text change (a v2) therefore needs edits in two other workstreams' files. The v1 planning templates are unchanged in this wave: the D13/D14 obligations and material rules reach every planning prompt verbatim through the policy data, which `packages/planning/test/templates.test.ts` proves. Suggest one role-to-template map in contracts before the first template revision.
